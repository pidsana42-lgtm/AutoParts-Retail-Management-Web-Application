## รายละเอียดการแก้ไข

- `frontend/nginx.conf`: CSP และ Cache-Control อยู่ระดับ server เพื่อไม่ทำให้ security headers เดิมหายจาก location; ไฟล์ assets/fonts ที่ไม่มีจริงตอบ 404
- `frontend/index.html`, `frontend/src/index.css`, `frontend/public/fonts/`: เปลี่ยนฟอนต์หลักเป็นไฟล์ภายในเว็บ รูปแบบตัวอักษรและน้ำหนักเดิมยังอยู่ แหล่งดาวน์โหลดบันทึกใน `SOURCES.json` และมีใบอนุญาตครบสามตระกูล
- `frontend/vite.config.ts`: ค่า `esbuild.legalComments` ที่มีอยู่ก่อนเริ่มงานทำให้ TypeScript build ไม่ผ่านกับ dependencies ปัจจุบัน จึงย้ายเจตนาเดิมไปใช้ `build.rolldownOptions.output.comments` สำหรับ Vite 8 และสร้าง `.vite/license.md` แยกเก็บประกาศใบอนุญาต
- `frontend/dist/`: build ใหม่ด้วยคำสั่งปกติ เนื่องจาก repository นี้ติดตาม dist และ Dockerfile ใช้ไฟล์ที่ build ไว้แล้ว
- เพิ่ม `frontend/scripts/test-security-headers.py` สำหรับทดสอบ config จริงผ่าน Docker โดยไม่เปิด host port ไม่เชื่อม backend/ฐานข้อมูลจริง และลบ container ทดสอบเมื่อจบ

## ข้อจำกัด CSP และการทดสอบ

CSP รองรับแผนที่, WebSocket ของโดเมนร้าน, รูปภาพภายนอกผ่าน HTTPS, PDF ใน iframe และ blob worker ที่มีอยู่ โค้ดพิมพ์ QR/barcode เดิมใช้ inline onload จึงอนุญาตเฉพาะ hash ของ `window.print();window.close();` ด้วย `unsafe-hashes` โดยไม่เปิด `unsafe-inline` สำหรับ script ทั้งหมด

ยังจำเป็นต้องมี `unsafe-eval` เพราะ worker ของ heic2any ใช้ `new Function` และ `unsafe-inline` สำหรับ style ที่ UI/หน้าพิมพ์ใช้อยู่ จึงไม่ใช่ strict CSP และการสแกนใหม่อาจรายงานข้อจำกัดเหล่านี้ การเลิกใช้ต้องปรับไลบรารี/รูปแบบ UI เพิ่มเติม ไม่ควรลบ directive จนทำให้ระบบเดิมเสีย

ยังอนุญาต Google Fonts สำหรับ Google Maps และหน้าต่างพิมพ์ตรวจนับสต็อกเดิมที่อยู่นอกขอบเขตงานนี้ การเปิดหน้าพิมพ์ดังกล่าวยังอาจสร้างคำขอไป Google Fonts ไม่ได้อ้างว่าเลิกใช้ฟอนต์ภายนอกครบทุกหน้าต่างของระบบ

แนวทางอ้างอิง: [การสืบทอด add_header ของ Nginx](https://nginx.org/en/docs/http/ngx_http_headers_module.html) และ [CSP สำหรับ Google Maps](https://developers.google.com/maps/documentation/javascript/content-security-policy)

## การกู้ Docker และตรวจ image จริง

ผู้ใช้อนุญาตให้ดำเนินการต่อหลังแจ้งผลกระทบของการรีสตาร์ท Docker แล้ว คำสั่ง restart ปกติหมดเวลา จึงใช้ `docker desktop stop --force --timeout 60` และ `docker desktop start --timeout 120` เพื่อกู้ Docker ที่ค้างจาก I/O error ไม่มีการล้าง cache, image หรือ volume ของงานอื่น พื้นที่ว่างหลังฟื้นระบบประมาณ 25–26 GiB

`virtual-office` กลับมา healthy และ `postgres` ตอบ `pg_isready` ว่า accepting connections ส่วน container เก่าชื่อ `nginx` ยังวน restart เพราะหา `backend:8000` ไม่พบ ตรวจ log พบ error เดียวกันตั้งแต่ `2026/09/21 13:00:00 UTC` ก่อนรีสตาร์ทรอบนี้ จึงไม่ได้แก้ config/เปิด backend ของโปรเจกต์เก่าที่อยู่นอกงานนี้

สร้าง image `autoparts-security-review:2026-09-21` จาก Dockerfile จริงสำเร็จ และเพิ่มตัวเลือก `--image` ให้สคริปต์ทดสอบ/สแกน เพื่อใช้ config และไฟล์เว็บที่อยู่ใน image จริงโดยไม่ mount ทับ ทดสอบโดยมีเฉพาะ certificate ทดสอบกับ API fixture ไม่มี backend/ฐานข้อมูลจริง ไม่มี host port ที่เปิดเพิ่ม

คำสั่งทำซ้ำจาก root ของ repository:

```sh
docker build -t autoparts-security-review:2026-09-21 frontend
cd frontend
python3 scripts/test-security-headers.py --image autoparts-security-review:2026-09-21
python3 scripts/scan-zap-local.py --image autoparts-security-review:2026-09-21
```

ZAP ใช้ passive baseline บนเครือข่าย Docker ภายใน (`--internal`) รายงานอยู่ที่ [HTML](zap-local-2026-09-21.html) และ [JSON](zap-local-2026-09-21.json) ไม่ได้ใช้ browser/AJAX spider หรือ active attack และไม่ได้สแกน production จึงไม่ครอบคลุมหน้าที่ต้อง login หรือการกดใช้งานจริง

ZAP รอบแรกยังแจ้ง `Cache-Control: no-store` ระดับ Informational จึงเติม directive ให้ครบตาม [คำแนะนำ ZAP 10015](https://www.zaproxy.org/docs/alerts/10015/) และสร้าง image/สแกนซ้ำ ไม่ปิดหรือ ignore กฎของ scanner

Browser runtime ยังไม่มี browser เชื่อมอยู่ จึงยังไม่ได้ทดสอบการกดใช้งานในเบราว์เซอร์และยังไม่ได้ deploy ผล 187 unit tests เป็นผลก่อนหน้านี้ เพราะรอบต่อมาปรับเฉพาะ infrastructure/test scripts ไม่ได้เปลี่ยนโค้ดธุรกิจ

## ผล ZAP รอบล่าสุดจาก image หลังแก้ Cache-Control

สแกนสำเร็จด้วย ZAP 2.17.0 และทดสอบ headers จาก image ล่าสุดผ่านทั้ง 10 กรณี รวม `nginx -t` ตรวจ syntax กับตรวจฟอนต์/ใบอนุญาตครบ หลังปิด OCR fallback สร้าง image และสแกนใหม่แล้ว Image ID ล่าสุด: `sha256:3406611e4196bc03b4b85a8813d67faa0a41e23e643e61cff7a698fb36e37abd`

ไม่พบ **CSP Header Not Set**, **Sub Resource Integrity Attribute Missing** หรือ **Re-examine Cache-control Directives** ในขอบเขตสแกนนี้ รายงานล่าสุดมี alert 7 ประเภท: High 0, Medium 4, Low 1, Informational 2 ทั้งนี้ console ของ baseline รวมกฎย่อย CSP เป็น rule 10055 จึงแสดง WARN-NEW 2 กลุ่ม ไม่ใช่คำเตือนเพียง 2 ประเภท ผล scan สำเร็จไม่ได้หมายความว่าไม่มีความเสี่ยงเหลือ

| รายการที่ยังพบ | ระดับ | การประเมิน |
| --- | --- | --- |
| CSP: Wildcard Directive | Medium | `img-src https:` รองรับ URL รูปภาพ HTTPS ที่ระบบเดิมยอมรับ การจำกัดโดเมนต้องตรวจแหล่งภาพจริงก่อน ไม่ควรปิดจนรูปของผู้ใช้หาย |
| CSP: script-src unsafe-eval | Medium | worker ของ heic2any เรียก `new Function`; ต้องเปลี่ยนวิธีแปลง HEIC/โหลด worker ก่อนลบข้อยกเว้นนี้ |
| CSP: script-src unsafe-hashes | Medium | รองรับ hash ของ inline handler พิมพ์ QR/barcode ในหน้าสต็อกเดิม การลบต้องแก้หน้าที่ใช้ handler ซึ่งอยู่นอกขอบเขตที่ผู้ใช้อนุญาตให้แก้ |
| CSP: style-src unsafe-inline | Medium | UI และหน้าพิมพ์เดิมใช้ inline style ต้องปรับการสร้าง style ก่อนบังคับ policy ให้เข้มขึ้น |
| Timestamp Disclosure - Unix | Low | ทั้ง 5 ตัวอย่างใน JSON ตรงกับรหัสสีของ html2canvas: CADETBLUE, CORNFLOWERBLUE, DIMGRAY, LIGHTSLATEGRAY, LAWNGREEN ไม่ใช่เวลาจากระบบ |
| Suspicious Comments | Informational | ยังเป็นข้อความเตือน runtime ของ React Router ตัวเดิม ไม่ใช่ข้อมูลลับ |
| Modern Web Application | Informational | เป็นลักษณะปกติของ SPA |

คำเตือน CSP 4 ประเภทเป็นข้อจำกัดที่ยังมีอยู่จริง ไม่ได้จัดเป็น false positive และไม่ได้ซ่อนด้วยการ ignore rule การแก้ให้หมดต้องพิจารณาโค้ดส่วนที่ใช้ร่วมกับงานของเพื่อนและทดสอบ browser ให้ครบก่อน deploy ไม่เปรียบเทียบจำนวน alert ตรง ๆ กับรายงานเดิมที่รวม third-party และมีขอบเขตการสแกนต่างกัน

## การตรวจสิทธิ์ API เพิ่มเติมและปิดช่องทางข้าม backend

การอ่านโค้ดและทดสอบ route พบสิ่งที่ passive scan ของหน้า SPA ไม่ได้ตรวจพบ:

- OCR ทั้ง 3 alias ยังส่งคำขอไป AI แม้ไม่มี JWT, token หมดอายุ/ลายเซ็นผิด หรือ role ไม่ถูกต้อง ยืนยันด้วย test server ที่นับจำนวนคำขอ ก่อนแก้ได้ HTTP 200 และมีการเรียก upstream จริงใน test; หลังแก้ได้ 401/403 และไม่เรียก upstream
- `/api/catalogs` ทั้งอ่าน/สร้าง/แก้/ลบและ `/extract-image` ไม่มี authentication เพิ่ม JWT และ role guard ให้ตรงกับพรีออเดอร์
- เคลม/คืนเดิมตรวจเพียง JWT เพิ่มการตรวจ role เพื่อปฏิเสธ token ที่ไม่มี role หรือเป็น role นอกระบบ เจ้าของ/พนักงาน/ผู้จัดการและ alias Admin เดิมยังเข้าถึงได้ การตรวจสิทธิ์อนุมัติ/ปรับราคาที่เข้มกว่าเดิมยังอยู่
- ฝั่งนำเข้าบิลและแคตตาล็อกเลิก fallback ไป AI ตรง ๆ เมื่อ backend ปฏิเสธหรือล้มเหลว รวมถึงนำ proxy `/ocr` ที่ข้าม Go ออกจาก Vite เพื่อไม่ให้ dev server เปิดทางอ้อมนี้
- `docker-compose.yml` จำกัดพอร์ต AI เป็น `127.0.0.1:8000:8000` โดย backend ยังติดต่อผ่าน Docker network เดิมได้ ต้อง recreate service เมื่อ deploy จึงจะมีผลกับเครื่องเซิร์ฟเวอร์

ฝั่ง local ถ้า AI อยู่พอร์ตอื่น ให้ตั้ง `OCR_SERVICE_URL` ใน environment ของ backend แทน `VITE_OCR_URL` และเรียกผ่าน Go เสมอ ไม่มีการเปลี่ยน provider/model หรือเรียก Gemini จริงในการทดสอบนี้

- Frontend tests นำเข้าบิล/พรีออเดอร์/เคลมและ HTTP services รวม test ที่ห้าม fallback หลัง 401/403/500 — **10 ไฟล์, 194 เคสผ่าน**
- `npm run build`, `go build -o /tmp/autoparts-security-backend main.go` และ build frontend Docker image — ผ่าน
- headers ของ image ล่าสุด 10 กรณีและ ZAP baseline รอบล่าสุด — ผ่านการรัน คำเตือน CSP 4 ประเภทยังคงอยู่ตามตาราง ไม่ได้อ้างว่า ZAP ไม่มี warning
- ตรวจ Compose แบบไม่แสดง environment/secret ยืนยันว่า AI port ผูกกับ 127.0.0.1

เปลี่ยน backend local จาก process เดิมเป็น binary ที่ build แล้ว โดยสำรอง binary เดิมไว้ก่อนและมีขั้นตอน rollback หากเริ่มไม่สำเร็จ รุ่นใหม่เริ่มได้ (`/ping` 200) และตรวจ HTTP ของ backend จริงในเครื่องโดยไม่ล็อกอิน 8 endpoint ได้ **401 ครบ**: catalogs, pre-orders, customer-claims, returns, OCR 3 aliases และ catalog extraction ไม่สร้างบิล/สั่งซื้อ/เคลมทดสอบในฐานข้อมูลจริง

ชุดตรวจนี้ไม่ครอบคลุมทุก API ของเพื่อน, WebSocket authentication, global JWT-secret configuration หรือความปลอดภัยครบวงจรของ mobile QR upload ซึ่งใช้ session capability แยกจาก staff JWT ไม่ได้แก้หรือถือว่าผ่านการตรวจประเด็นเหล่านั้นจากผล 150 กรณีนี้

Browser ในแอปยังไม่มีการเชื่อมต่อ ได้ถามทางเลือกทดสอบด้วย Playwright แยกไว้แล้ว ยังไม่ได้รันทดสอบ browser/CSP ของแผนที่ การพิมพ์ หรือ HEIC จริง และยังไม่ได้ deploy production
